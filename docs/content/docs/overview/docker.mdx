# Docker Deployment

## Use the published image

```bash
git clone git@github.com:basketikun/infinite-canvas.git
cd infinite-canvas
docker compose up -d
```

Open `http://localhost:3000`.

## Build locally

```bash
docker compose -f docker-compose.local.yml up -d --build
```

To test the Canvas BFF infrastructure separately, start the isolated PostgreSQL and MinIO stack:

```bash
docker compose -f docker-compose.bff.local.yml -p infinite-canvas-bff up -d --build
powershell -ExecutionPolicy Bypass -File scripts/smoke-bff-stack.ps1
```

This provisions PostgreSQL 16, runs the checked-in BFF migrations, creates the `canvas-media` bucket in MinIO, and starts the persistent BFF on `http://localhost:17372`. The BFF uses PostgreSQL for account/workspace records and MinIO for media in non-test environments. Run `npm run test:integration` in `canvas-bff` with the stack connection variables to verify durable writes and signed media reads. Stop it with `docker compose -f docker-compose.bff.local.yml -p infinite-canvas-bff down`; add `-v` only when intentionally deleting test data.

## OVH production stack

The repository includes a production Compose stack and an SSH deployment workflow for `ovh-sing`. The stack keeps the frontend, BFF, PostgreSQL, and MinIO ports on loopback; host Nginx exposes `https://canvas.v-claw.org` for the iframe application and `https://media.canvas.v-claw.org` for signed MinIO reads. The media host preserves the S3 request path required by the signature, permits only `GET`/`HEAD`, and returns CORS headers only for the Canvas origin.

Create `/srv/infinite-canvas/.env.production` on the server from `deploy/ovh-sing/env.production.example`, use mode `600`, and set the same `SUB2API_CANVAS_BFF_SECRET` in Sub2API. Create DNS records for both `canvas.v-claw.org` and `media.canvas.v-claw.org`; the deploy script issues one certificate containing both names on the first run. Configure these GitHub Actions secrets for automatic deployment on pushes to `main`: `OVH_SSH_HOST`, `OVH_SSH_USER`, `OVH_SSH_PRIVATE_KEY`, and `OVH_SSH_KNOWN_HOSTS`.

Run the stack manually on the server with:

```bash
DEPLOY_SHA=manual bash deploy/ovh-sing/deploy.sh
```

The script validates production secrets, DNS, TLS, Compose configuration, database migration, BFF readiness, and same-origin HTTPS health before reporting success. It intentionally stops before changing traffic when any prerequisite is missing.

## Documentation image

The documentation in `docs/` is a separate Next.js standalone application with server capabilities.

```bash
cd docs
docker compose up -d
```

To build it from the current source:

```bash
cd docs
docker compose -f docker-compose.local.yml up -d --build
```

The main application container only runs Next.js. Canvases, My Assets, generation history, and API keys are stored in the browser by default, while prompt repositories are fetched directly by the frontend. No persistent data volume is required for this data.

## Optional analytics

No analytics are enabled by default. A deployment can enable GA4, Baidu Analytics, or both at runtime:

| Variable | Description |
| --- | --- |
| `ANALYTICS_GA4_ID` | Google Analytics 4 measurement ID (`G-XXXX`) |
| `ANALYTICS_BAIDU_ID` | Baidu site ID, the hash after `hm.js?` |

```yaml
services:
  app:
    image: ghcr.io/basketikun/infinite-canvas:latest
    ports:
      - "3000:3000"
    environment:
      ANALYTICS_GA4_ID: G-XXXXXXXXXX
      ANALYTICS_BAIDU_ID: e8263761cc5c32f5f7a855b8203b965a
```

SPA route changes automatically report page views to enabled providers. Only configure analytics IDs on sites you control, and do not commit them to the repository.
